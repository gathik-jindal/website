Curious, careful, hands-on

I like problems where the obvious answer is not quite right: four data engines that should behave the same but don't, a model that looks accurate until you put the random baseline next to it, or a dozen coding agents quietly overwriting each other's work. Most of what I build starts as a question like that.

The work so far spans digital logic, computer architecture, games, distributed backends, HPC, graphics, and ML research, mostly built with teammates at IIIT Bangalore, in the lab, and at hackathons. The common thread is wanting to know how a thing works one layer below where I'm using it.

Built to be measured, not just demoed

Down to the datapath

I like knowing what is under the abstraction, which is how I ended up writing logic simulators, a MIPS processor, and a physics engine from scratch.

Same steps, fair numbers

When comparing things, I hold everything else fixed: identical ETL logic across four engines, and a baseline next to every model.

Targets are not results

A design target gets labelled as a target. Reported numbers are the ones I actually measured.

Ship where people can try it

A Discord bot people played on a live server, WebGL demos that run in the browser, and this site.

Learn in public

My Obsidian notes are published here as I write them, rough edges included.

Better with a team

Most of these projects were built with three to six teammates. Splitting a hard problem well is half of solving it.
